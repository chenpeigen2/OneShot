## 1. 背景与问题陈述

### 1.1 为什么是它

OneShot 的 sidecar 体系里，sidecar token 是**唯一一道**"绕过 PB 直调 handler"的凭据：PB 侧路由经中间件鉴权后用烘焙进 hooks 的 token 把请求转发到控制服务器 `/sidecar/{service}/{action}`（README 明示"服务间共享 token"）；反过来，任何持有该 token 的进程都可以**跳过全部 PB collection 规则**直调任意 handler（sidecar-realtime 套件已钉住 401/200 边界，说明这条直访路径真实存在且被测试认作公开面）。这样一个高价值凭据，其卫生状况目前只靠两行代码的善意（`packages/core/src/sidecar.ts:27-28` 创建时 `mode: 0o700/0o600`），没有任何自动化保障，且**项目自己的测试编排器正在违反这条不变式**。

本迭代要收敛的问题清单（全部来自代码事实 + 测试 agent 上轮遗留的覆盖建议）：

1. **token 母本权限不自愈**：`getOrCreateSidecarToken` 只在"创建"时设置 `0o700/0o600`；文件已存在时直接读出返回，权限永不纠正。任何外部途径（旧版本升级残留、其他工具预写、手工 touch）留下的宽松权限会永久保持。
2. **自家编排器以 0644 写 token**：`tests/run-e2e.mjs:122` 用 `writeFileSync(path, token)`（默认 0644，umask 依赖）预写 token——CI 与每位贡献者机器上，这条不变式天天被违反，无断言拦截。发布虽发生在写 token 之后（publish 会读到该文件），但"宽松权限窗口"贯穿整个编排期。
3. **token 出现的三个位置无人看守**：`.oneshot/sidecar-token`（母本）、`pb_hooks/<svc>.pb.js`（明文烘焙，`hooks-compiler.ts:172`——设计使然，PB JSVM 运行时需要）、控制服务器内存。母本权限与"输出不泄漏"零断言。
4. **doctor 的 stdin 安全只有隐式覆盖**：R1 AC-11 自己承认"隐式覆盖；无需独立断言"——但 doctor 的核心卖点恰是"绝不读 stdin"，这条承诺没有一处显式测试（`spawnSync` 的 stdin 管道默认立即 EOF，测不出"读了 stdin 会挂起"）。
5. **secret 卫生零回归防线**：doctor 全程处理超管密码与 token（`doctor.ts:126-127, 189`），"密码/token 不出现在 stdout/stderr"今天恰好成立，但没有任何断言阻止未来某次 detail 文案改动把它带出来。sidecar 的 401 响应体同理（现有断言只查状态码，不查 body 是否回显合法 token）。
6. **handler 路径信任边界决策未落地**：`resolveAction`（`manifest.ts:131-137`）对 handler 路径无项目根约束（`../`、绝对路径均可），测试 agent 上轮判定"超管可引用项目外 .ts，属可接受风险"——但这个决策既没写进 README 的"架构与已知约束"，也没有一条断言把现状钉住。未来若有人无意收紧（或放宽），不会有任何红灯提示这是行为变更。

### 1.2 候选对比（为什么不是别的）

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| (a) 每服务独立实例（dedicated: true） | 否 | 引擎编排从"单进程"变"进程池"：端口分配、多数据目录、生命周期管理、publish 扇出、codegen 的 per-service baseUrl 映射、doctor 多实例语义——改动面贯穿 core/cli/engine 全部路径，e2e 还需要多实例编排扩展。R1 对备份调度的风险论证（改动面超出单迭代）在此被放大一个量级，是 Roadmap 里最重的大件，不该在测试加固可完成的窗口期抢跑。 |
| (b) 模板市场 | 否 | "市场"= 分发渠道：registry 协议、模板包 schema 序列化（当前模板是 TS 函数注册表 `templates-ts/registry.js`）、git/网络拉取与供应链校验。单迭代最多做"本地路径 init"切片，配不上"市场"命名且验收退化为文件复制断言。模板 schema 已就绪是指注册表结构，外部化是另一个设计课题。 |
| (c) 备份调度 / 记录浏览增强 / 监控面板 / 上传辅助 | 否 | R1 已论证：cron e2e 等待脆弱、UI 行为超出 fetch+spawnSync 断言能力、双语言生成器改动面最大验收路径最弱。本轮无新信息，维持落选。 |
| (d) **sidecar 信任边界与凭据卫生加固** | **是** | 三条遗留覆盖建议（doctor stdin 显式覆盖 / token 权限断言 / handler 路径边界）天然共属"sidecar 信任边界"一个主题，可打包成一个内聚迭代；且分析发现两处真实缺陷（run-e2e.mjs 以 0644 写 token、getOrCreateSidecarToken 不自愈）——这不是"补测试"，是"修不变式 + 把不变式钉进 CI"。全部验收走既有 harness 模式（fetch + spawnSync/execFileSync + statSync），零功能风险，天然不威胁既有 84 项断言。 |

### 1.3 一句话定位

R2 = 把 sidecar 信任边界的盲区收敛成一条自动化防线：**token 权限不变式**（自愈修复 + 编排器源头修复 + 断言）、**doctor 非交互承诺与 secret 卫生的显式回归钉**、**handler 路径边界的文档化与现状钉住**——全部在既有 `tests/suites/*.test.mjs` 模式内验收。

## 2. 用户故事

1. 作为**多用户主机上的自托管用户**（办公室工作站 / 家庭服务器 / 共享 CI runner），我从不记得手工 `chmod 600 .oneshot/sidecar-token`，以便系统在任何一次 `publish` / `console` 启动时自动把 token 母本收敛到仅属主可读，同机其他用户无法直调我的 sidecar handler。
2. 作为**从旧版本升级的用户**，我的 `.oneshot/sidecar-token` 是旧版创建的 0644 文件，以便升级后第一次发布自动修复权限，且 token 值不变（已烘焙进上次发布的 hooks 产物，轮换会断链）。
3. 作为**贡献者/维护者**，我改动 doctor、sidecar 或凭据处理代码，以便 CI 在我引入"读 stdin"、"打印密码/token"、"放松文件权限"中任何一项时立刻红灯，而不是靠 code review 人眼把关。
4. 作为**运维者**，我阅读 README 的"架构与已知约束"，以便明确 sidecar 的信任边界：token 在哪里出现、谁能调用 handler、哪些暴露面是设计使然（hooks 烘焙）、哪些已被自动化防线看守。

## 3. 功能需求

约定：现有 6 套件 84 项断言**冻结**（文件逐字不动）；新增套件 `tests/suites/security.test.mjs` 追加到 runner 套件列表**末尾**（doctor 之后，延续"污染型套件排最后"的纪律）。权限类断言仅在 unix 语义下有效（`process.platform !== 'win32'` 守卫，CI 为 ubuntu-latest，本机 darwin）。

- **FR-1 token 母本权限自愈（core）**：`getOrCreateSidecarToken(root)` 在返回**已存在**的 token 文件前，对 `<root>/.oneshot/` 目录与 token 文件强制 `chmod 0o700 / 0o600`（幂等，权限已正确时为无害操作）。**绝不重生成内容**：已存在即原样返回（现行为保持），token 值改变会造成"已烘焙进上次发布产物的旧 token"与"新 token"断链窗口（见坑位 1）。创建路径行为不变。
- **FR-2 编排器源头修复**：`tests/run-e2e.mjs` 预写 token 改为 `writeFileSync(path, token, { mode: 0o600 })`（目录 `mkdirSync` 同样带 `mode: 0o700`），与 core 创建路径语义一致。token 内容不变（sidecar-realtime 套件从该文件读值构建请求头，内容不变即零影响）。
- **FR-3 权限不变式断言**：security 套件断言两层——(i) 真实夹具：fixture `.oneshot/sidecar-token` 文件 mode `0o600`、`.oneshot/` 目录 mode `0o700`（runner 已预发布，FR-1 自愈 + FR-2 源头修复双重兜底后必然成立）；(ii) 核心行为：临时目录手工构造 0644 token + 0755 目录，直接 import `@oneshot/core` dist 调 `getOrCreateSidecarToken`，断言返回内容与预写值**字符串相等**（不轮换）且权限被纠正。
- **FR-4 doctor 非交互承诺的显式覆盖**：security 套件用 `spawn`（非 spawnSync）运行 `doctor --json`，条件取"最可能诱导交互实现的路径"：无凭据（显式排除 `ONESHOT_SUPERUSER_EMAIL/PASSWORD`）+ 裸 cwd（无 `.env` 可加载）+ stdin 为**打开且父进程永不写入、永不关闭**的管道。断言进程在 15 秒内自然退出、退出码 0、`credentials` 项 `warn`。若实现读了 stdin 将永久挂起 → 超时 kill → 断言失败。
- **FR-5 secret 卫生断言**：
  - doctor 正常路径运行（真实凭据）后，stdout + stderr 全文**不包含**超管密码子串，也**不包含** sidecar token 值（token 从 fixture 文件读出后比对）；
  - sidecar 直访携带错误 Bearer → 401 且响应体**不回显**合法 token 子串（防"debug 输出 expected token"类回归）。
- **FR-6 handler 路径边界：行为保持 + 现状钉住 + 文档化**：
  - 行为**不变**：项目外 handler（如 `'../outside-handler/handler.ts#stats'`）继续被 `validateConfig` 接受（超管可信，测试 agent 结论维持；收紧会破坏"引用共享 hooks 库"的合法用法且属行为变更）；
  - 钉现状：security 套件构造临时项目副本，其 config 引用项目外 handler 文件，跑 `doctor --json` 断言 `config` 项 `ok`——把"今天接受越界 handler"钉进 CI，未来任何收紧/放宽都会红灯提示这是有意识的行为变更；
  - 文档化：README"架构与已知约束"增补 sidecar 信任边界小节（token 三处出现位置、直调边界、越界 handler 属超管自担风险）。
- **FR-7 文档与计数修正**：README 测试计数**已过期**（写 69，实际 84）、CI yml step 名写 65——本迭代一并修正：README 更新为实际值 + 套件列表加 `security`；CI yml 计数同步。
- **FR-8 零回归**：既有 6 套件文件逐字未动；`run-e2e.mjs` 除 FR-2（token mode）与套件数组追加 `'security'` 外无改动；doctor 的检查项清单不变（新增检查项会破坏 doctor 套件 AC-1 的固定顺序断言 `config,engine,connectivity,credentials,snapshot,hooks,disk`——旧套件冻结的硬约束）。

## 5. 非目标（本迭代明确不做）

1. **不改变 token 烘焙进 hooks 产物的设计**：`pb_hooks/<svc>.pb.js` 明文含 `Bearer <token>`（`hooks-compiler.ts:172`）是设计使然——PB JSVM 运行时需要它发 `$http.send`，替代方案（运行时读文件/把 token 拷进共享卷）暴露面相同甚至更差。本迭代只收敛 `.oneshot/sidecar-token` 母本权限并建立不变式，烘焙面的缓解（卷隔离、主机用户卫生）写入 README 文档。
2. **不给 `pb_hooks/*.pb.js` 产物设 0600**：PB 容器必须可读；docker compose 双容器（pb + control）共享卷、用户可能不同，收紧会直接破坏自托管部署。
3. **不引入 token 轮换（rotation）**：自愈绝不重生成（理由见坑位 1）。轮换需要"重发布烘焙 + PB 冷重启"编排，属独立课题。
4. **不收紧 handler 项目外引用**：行为保持（超管可信）；本迭代只做文档化 + 现状钉住（FR-6），任何收紧留待专门迭代评估"共享 hooks 库"真实用例后决策。
5. **不给 console/manifest API 增加新鉴权机制**：401/413/415/4xx 校验拒绝已有 manifest 套件覆盖，本迭代不重复断言、不改动。
6. **不给 doctor 新增检查项**：旧套件冻结的硬约束（FR-8），新增检查项必然破坏固定顺序断言。
7. **不做 dedicated 实例 / 模板市场 / 备份调度 / 记录浏览 / 监控面板 / 上传辅助**：Roadmap 大件维持落选（见 1.2），留待后续迭代。
8. **不做 Windows 权限语义适配**：权限断言以 `process.platform !== 'win32'` 守卫跳过；README 计数按 unix 口径标注。

### 实现注意（坑位提示）
1. **自愈绝不重生成 token**：旧 token 已烘焙进上次发布的 `pb_hooks` 产物，PB→sidecar 转发依赖它。若自愈实现误用 `randomBytes` 重写，下次 publish 前所有 sidecar action 静默 502/401。AC-2 的"返回值 === 预写值"断言就是防这个。
2. **只碰母本，不碰产物**：`chmod 0o600` 只作用于 `.oneshot/sidecar-token`；对 `pb_hooks/*.pb.js` 做同样的事会破坏 docker compose 双容器部署（非目标 2）。实现时不要顺手"加固"产物目录。
3. **stdin 测试必须用 spawn 而非 spawnSync**：spawnSync 的 stdin 管道立即 EOF，读 stdin 的实现会拿到 EOF 正常返回——测不出挂起。spawn + 永不写入/关闭的管道才构成真实诱惑路径。且 env 必须显式排除两个 superuser 变量、cwd 必须无 `.env`（`loadDotEnv` 按 cwd 查找），否则凭据存在走不到 warn 分支。
4. **doctor 检查项清单不可动**：`doctor.test.mjs` AC-1 断言 checks 顺序为 `config,engine,connectivity,credentials,snapshot,hooks,disk`——给 doctor 加检查项（如"权限检查项"）会让旧套件红灯。这也是本迭代选 doctor 钉越界 handler 现状、而非新增检查项的原因。
5. **security 套件排末尾**（doctor 之后）：虽只读 fixture、临时路径自清理，仍延续 R1"污染型/依赖型套件最后"的纪律，把对 fixture 状态的假设（token 已发布、快照新鲜）锁死在既有套件之后。
6. **chmod 的时机与幂等**：publish 每次都调 `getOrCreateSidecarToken`（provisioner 无条件调用），自愈放在"已存在分支"意味着每次发布/控制台启动都会修正——不要只在创建分支加 mode（那正是今天的缺陷）；`chmodSync` 对已正确权限是无害系统调用，无需先 stat 比较再决定。
7. **win32 守卫**：`statSync().mode` 在 Windows 无 unix 语义，AC-1/AC-2 的权限断言必须整块置于 `if (process.platform !== 'win32')` 内；README 计数注明按 unix 口径（CI ubuntu-latest 与 macOS 开发机均不受影响）。
