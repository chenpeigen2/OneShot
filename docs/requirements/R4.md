## 1. 结论摘要

当前问题不是“文件太少”这么简单，而是几类不同的变化原因集中在同一个入口：

- 发布编排、PocketBase HTTP 调用、认证规则、种子、快照和客户端生成集中在 `provisioner.ts`。
- CLI 参数解析、所有命令、dev 生命周期和控制服务器运行时集中在 `cli/index.ts`。
- 控制台登录、仪表盘、记录、备份和编辑器集中在一个 React 文件。
- 图书示例把 PB 请求、事务、进程内锁、权限和全部业务 action 放在一个 sidecar 文件。

应当拆分，但目标不是更多文件，而是更清楚的模块接口和更集中的修改位置。先做内部模块归位，不拆更多 npm 包、不改变 `@oneshot/core` 现有公共入口、不引入外部依赖。

优先级最高的功能修正不是模板市场或前端脚手架，而是：

1. 完整、版本化的发布快照；
2. 可靠的 `DevRunner`（冷重启、串行 watch、就绪检查）；
3. 发布计划/执行分离与并发锁；
4. sidecar 身份验证和最小权限；
5. 多环境产物隔离及 action 类型化。

**横切强制约束**：所有阶段禁止 `any`，完整规范见 `AGENTS.md`。未声明模型的旧接口使用 `unknown` 并收窄，不得继续生成或复制 `any`。

## 4. 真正值得建立的模块接缝

### 4.1 publish：纯 plan 与副作用 execute 分离

当前 `publish()` 一边读取远端状态一边直接写 PB、文件和生成物（`packages/core/src/provisioner.ts:128-443`）。仅把这段拆成几个文件，仍然会得到同样的隐式时序和失败恢复问题。

建议接口：

```ts
const plan = planPublish(config, remoteState, previousSnapshot, options)
const report = await executePublish(plan, dependencies)
```

- `planPublish`：纯计算，产出 auth/collection/schema/index/rules/hooks/meta 的有序操作。
- `executePublish`：处理 Admin API、种子 relation 查询、文件写入和客户端生成。
- `PocketBaseAdmin`：生产 HTTP adapter；测试使用内存 fake。
- `PublishReport`：继续作为公共结果，增加计划 ID/失败步骤时保持向后兼容。

收益：`publish --dry-run`、doctor 漂移说明、并发锁、watch 日志和单元测试都复用同一计划，而不是各写一套 diff。种子 relation 等必须在线解析的步骤留在 execute，不假装整个发布都能离线决定。

### 4.2 DevRunner：统一生命周期，而不是在 doDev 里堆 if

当前 dev 在启动后执行 publish + sidecar rebuild（`packages/cli/src/index.ts:113-131`），watch 仅 debounce 后 `void run()`（`:148-153`），没有串行发布、JSVM 后冷重启或路由就绪协议。

建议 `DevRunner` 的小接口：

```ts
await runner.start()
await runner.runOnce()
await runner.close()
```

内部负责：

- 初次发布失败时不得显示“就绪”；
- latest-wins 串行队列，禁止上一次发布未结束又开始下一次；
- JSVM 产物变化后冷重启本地引擎，并等待健康检查；
- sidecar registry 热替换；
- 对可安全探测的 action 做路由存在性检查，避免 PB health 200 但 `/api/oneshot/*` 仍 404；
- 明确 `starting / ready / publishing / error` 状态及日志。

### 4.3 React：纯状态变换与视图分离

控制台编辑器的 draft 克隆、字段重命名、options 文本和校验目前集中在 `packages/console/src/App.tsx:404` 起。应先把这些纯操作下沉到 `editor/model.ts`，React 只负责事件和渲染。这样拆分可以直接复用现有 console-ui 浏览器路径验收，而不是靠肉眼确认文件搬家。

## 5. 功能与架构优化优先级

### P0：先修正确性和开发内循环

#### 5.1 完整、版本化的发布快照

**事实**：`buildSnapshot()` 只返回 services（`packages/core/src/pb-mapping.ts:321`）；collection 字段只记录字段名（`:328`）。字段 kind/options、indexes、auth/managed/RBAC、batch 都没有进入哈希，而 doctor 正好复用它做漂移检测（`packages/cli/src/doctor.ts:203`）。

影响：修改认证规则、托管字段、字段类型/约束或索引，doctor 可能仍认为本地与远端一致。

建议：

- 定义 `snapshotVersion: 2`，覆盖会影响发布的完整配置；
- 保留 `services` 供控制台展示，新增完整定义而非继续堆进现有浅快照；
- doctor 识别旧版本并提示“快照格式升级，请重新 publish”，避免把升级误报成普通漂移；
- 新增 auth、字段 options、indexes、batch 的哈希变化断言。

#### 5.2 DevRunner 冷重启、串行 watch 与就绪协议

**事实**：`doDev()` 没有 JSVM 后引擎重启；watch 可以 `void run()` 重叠发布（`packages/cli/src/index.ts:113-153`）。本机图书实例已经实际出现过 PB health 正常但 action 路由 404，需要手动冷重启。

建议按 4.2 实施，并增加“初次启动 + 连续两次变更 + 发布失败恢复 + action 路由就绪”的集成测试。

#### 5.3 发布锁、计划与失败状态

**事实**：watch 可无等待触发发布；控制台写回又是另一条 publish 路径。控制台先备份并写 manifest（`packages/cli/src/control-api.ts:110-111`），随后才 publish（`:115-120`），失败时文件和内存/远端可能处于不同阶段。

建议：

- 每项目一把发布互斥锁，watch 与控制台写回共用；
- 先形成计划，再执行；禁止两个执行器交叉写同一目标；
- manifest 使用临时文件 + 原子替换，并明确 publish 失败后的 dirty 状态/恢复策略；
- 不宣称整个 PB 发布是一个数据库事务；提供可恢复步骤、明确失败阶段和重放入口。

### P1：权限、隔离与接口类型

#### 5.4 sidecar 身份验证与最小权限

**事实**：sidecar 在静态 token 通过后直接使用请求体中的 `payload.auth`（`packages/core/src/sidecar.ts:165-170`）。README 已明确直调信任边界（`README.md:212`），所以这里不是声称存在未授权远程漏洞，而是部署到非本机前的必要加固。

同时，core 创建系统账号时硬编码 `role: 'librarian'`（`packages/core/src/sidecar.ts:201-209`），将图书业务角色渗入通用框架；发布器还对所有项目无条件创建账号并签发一年 token（`packages/core/src/provisioner.ts:316`），即使已有 `hasSidecarActions()` 可判断是否需要（`packages/core/src/sidecar.ts:231`）。

建议：

- sidecar 用转发用户 token 向 PB 验证并覆盖 `ctx.auth.id`，不信任请求体自报身份；
- core 不再设置 `librarian`，系统写规则明确绑定服务账号身份；
- 至少只在存在 sidecar action 时创建系统账号；进一步按声明的系统写需求授权；
- 增加伪造 auth.id、过期用户 token、无 sidecar 项目不创建长效凭据的回归断言。

#### 5.5 多环境产物隔离与多项目所有权

**事实**：`env` 会改变目标 PB，但默认 hooksDir 仍是项目根 `pb_hooks`（`packages/core/src/provisioner.ts:360`）。现有 staging 测试显式传入独立 `staging-hooks`（`tests/suites/env-collections.test.mjs:35`），默认路径没有同等隔离验证。路由又只含 service/action（`packages/core/src/hooks-compiler.ts:165`），同一路由在不同项目间没有命名空间。

建议：

- 默认产物按环境隔离，例如 `.oneshot/envs/<env>/hooks`；远程发布必须显式配置远程 hooks 通道；
- 检测同 PB 上 service/action 与 hooks 的所有权冲突并 fail fast；
- 是否升级为 project 命名空间路由作为后续兼容决策，不在文件重构中顺手改变 URL。

#### 5.6 action input/output 与生成客户端类型

**原状（本轮改造前）**：action 输入曾是 `Record<string, any>`、返回曾是 `Promise<any>`；create/update 也合并 `Record<string, any>`；单值 select 只生成 `string`。`ActionDef` 目前没有输入输出模型（`packages/core/src/schema.ts:132`）。

**当前进展**：生成 action 已改为 `unknown`，select 已生成字面量联合，公开注册 DTO 已排除 managed 字段，`defineSidecarAction` 已提供运行时 decode 接缝，生成记录已对齐 PocketBase `RecordModel`。尚未完成的是可选 input/output 声明及由同一份声明驱动前后端类型与校验。

建议：

- 给 action 增加可选 input/output 声明，复用字段 DSL；
- 生成输入/输出类型与两个 runtime 共用的运行时校验；
- select 生成字符串字面量联合；
- public register 类型排除 managed 字段，管理端创建用户另用明确的受控入口；
- 图书 handler 改用类型化 `SidecarCtx`，不再使用 `ctx: any`。

### P2：体验和交付效率

- `useRecords` 当前每个 realtime 事件都 reload（`packages/core/src/codegen/ts.ts:201`）：增加短防抖、共享订阅和重复请求合并，保留现有过期响应保护。
- 角色 DSL：`managed` 已解决注册/自助更新安全，但规则里的角色名仍是裸字符串，可再做角色单一真源与拼写校验。
- `oneshot gen web`：可以生成 React 骨架，但应放在核心接缝稳定之后，避免把当前运行时问题复制到每个新项目。
- CI 目前只有 Ubuntu（`.github/workflows/ci.yml:10`）：增加 Windows 定向 core/library smoke，覆盖路径、junction 与进程生命周期，不必把完整浏览器矩阵翻倍。CI step 名仍为 137（`.github/workflows/ci.yml:32`），实施时与真实计数同步。

## 6. 分阶段实施建议

### 阶段 1（推荐的最小第一步）：发布模块归位 + 快照修正

范围：`provisioner.ts`、`pb-mapping.ts`，以及必要的测试。

1. 抽出 `pocketbase/admin.ts`、`auth/*`、`publish/collections.ts`、`publish/seeds.ts`、`publish/snapshot.ts`；
2. `publish()` 保持公共签名与执行顺序；
3. 引入纯 `planPublish()` 供内部使用，暂不公开 dry-run；
4. 快照升级为完整版本，doctor 增加旧快照升级提示；
5. 新增快照覆盖断言，保持所有现有行为测试通过；
6. 清理本阶段触及模块的存量 `any`，动态输入先 `unknown` 再收窄，不用双重断言绕过。

验收：

- `pnpm build`；
- 根 E2E 9/9（当前 140 项 + 新增断言）；
- 图书 45 API + 6 浏览器；
- 生成物 diff 为空；
- 本阶段触及模块 `any` 清零，新增 AST 类型检查通过；
- `git diff --check`。

### 阶段 2：CLI 命令拆分 + DevRunner

先移动命令，后用 `DevRunner` 接管 dev 生命周期。加入串行 watch、冷重启、健康/路由就绪与失败恢复测试。CLI 帮助和参数保持兼容。

### 阶段 3：console、图书前端与图书 sidecar 分功能模块

保持路由、文案和交互不变。编辑器纯 model 与 React 分离；图书 sidecar 入口只 re-export。同步清理这些模块的 `any` 并改用明确模型。使用 console-ui 和图书浏览器测试逐条验收，不以“能编译”作为完成标准。

### 阶段 4：发布锁、sidecar 最小权限、多环境/多项目隔离

这些会改变运行时行为，放在文件归位之后，逐项增加伪造身份、并发发布、默认多环境产物、路由冲突测试。

### 阶段 5：action 类型和生成客户端增强

可选 input/output 声明保持向后兼容；未声明的旧 action 生成 `unknown`，不得生成 `any`。先 TS，再同步 Dart，避免一次修改所有调用方。增加严格类型检查、运行时校验、select 字面量和生成物 `no-any` 断言。

## 7. 明确不做

- 不按“一个函数一个文件”碎片化，不制造大量只有转发的浅模块。
- 不手改 `web/src/api`、`pb_hooks`、`dist` 等生成物。
- 不立即拆更多 npm 包，不引入新框架/状态库/ORM。
- 不为假想中的第二种数据库提前抽象通用 adapter。
- 不把目录搬家、DevRunner、sidecar 权限、多环境和 action 类型一次性塞进同一个大 PR。
- 不把 `unknown` 或 `Record<string, unknown>` 当作已知领域模型的万能替代品，不用双重断言把 `any` 禁令变成形式合规。
- 不在重构中改变现有 action URL、公共 `publish()` 接口或生成客户端目录。

---

## 8. 最终建议

下一轮只选 **阶段 1**：先把发布这条主线整理成“PB adapter + 纯计划 + 受控执行 + 完整快照”，同时保持 `publish()` 和全部测试兼容。它能直接回应代码聚合问题，也为后续 DevRunner、dry-run、doctor、发布锁提供同一个接缝。

不要同时拆 console、图书 UI、CLI、sidecar 和全部生成器。阶段 1 验证稳定后，再按上述顺序推进。
