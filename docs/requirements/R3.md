- 状态：已选定，待实现
- 迭代：本迭代唯一需求
- 作者：产品 agent
- 日期：2026-10-25

## 1. 背景与问题陈述

### 1.1 为什么是它

OneShot 现有 7 套件 99 项断言全部是 HTTP / 进程 / 文件系统级（fetch + spawnSync + stat），而 `packages/console`（React 控制台，`App.tsx` 约 735 行）是这个仓库仅次于 core 的产品面，测试覆盖**为零**：登录流、仪表盘渲染、记录浏览、编辑器写回、备份面板，全部只靠人眼回归。这不是"下一个功能缺测试"，是一个已知的**结构性缺口**——R1 否决控制台候选时的原话是"现有 e2e 框架是 HTTP/进程级，无浏览器断言能力，UI 行为无法验收"。

但把 R1/R2 的否决理由读到底，会发现三件事：

1. **被测环境早已存在**。runner 每次全量 e2e 都拉起控制服务器（`TEST_CTRL` = `http://127.0.0.1:7861`），它托管 `packages/console/dist` 的完整 SPA（`console-server.ts` 的 SPA fallback）并连着主实例 PB——浏览器测试要的一切（构建产物、活的 PB、真实 manifest）每次 CI 都在跑，缺的只是"眼睛"。
2. **最复杂的写路径只覆盖了一半**。编辑器写回是全仓库最复杂的链路：draft 状态组装 → 字段改名映射 → options JSON 解析 → 客户端校验 → `POST /api/manifest` → `.bak` 备份 → 序列化写回 → diff 式发布 → 成功横幅。manifest 套件只覆盖了"POST 之后"的 HTTP 一段；"用户在 UI 里操作"到"POST 发出"之间（React 状态、renameField/optionTexts 映射、save 前校验）零覆盖，而这恰是最容易在 UI 重构时悄悄改坏的部分。
3. **R1/R2 的否决是"没有工具"，不是"不可能"**。R1 否决记录浏览增强、R2 维持否决，理由都是 harness 没有浏览器能力。连续两轮绕着走之后，正解不是继续绕，而是把能力本身作为交付物：R3 交付后，R1 否决的候选 a（记录浏览增强）自动解锁为可验收需求，控制台从此不再是不设防区域。

### 1.2 候选对比（为什么不是别的）

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| (a) 控制台记录浏览增强（过滤/排序/搜索） | 否（本迭代） | R1 的否决依据（无法验收 UI）在 R3 交付后失效，它是 R3 的**首个受益者**、R4 的首选。但本迭代若"能力 + 功能"一起做，改动面叠加（新测试基建 × 新 UI 功能），风险翻倍且互为干扰；先交付能力，功能在下一轮以可验收姿态进入。 |
| (b) `oneshot status` / 监控面板 | 否 | doctor 已覆盖引擎/连通性/凭据/快照/磁盘五环，status 的真正增量（引擎进程存活、sidecar 可达、日志尾、备份清单）价值薄，且进程存活检测需要 `engine up` 新编排才能在 e2e 验收。本质是"doctor 2.0"，与 doctor 的差异化撑不起一个迭代。 |
| (c) 生成客户端文件上传辅助 | 否 | R1 论证维持：TS + Dart 双生成器同时改动、需新增含 file 字段的 fixture、e2e 只能断言生成物内容（真要跑生成的客户端需新编译运行管道）。改动面最大、验收路径最弱，无新信息。 |
| (d) 备份自动调度（PB cronAdd） | 否 | R1 论证维持：cron 真实触发等待脆弱（最快 1 分钟/次），断言编译产物则是弱验收；README 已记录 JSVM 可靠面多个坑，cronAdd 属未实测区域。无新思路，不翻案。 |
| (e) **console 构建产物浏览器 E2E** | **是** | 纯测试侧增量：1 个 devDependency + 1 个 CI step + 1 个新套件 + runner 数组追加 1 行，产品代码零改动，天然不威胁既有 99 项断言；被测环境（TEST_CTRL 托管 dist SPA + 主实例）在每次 e2e 中已存在，runner 零编排改动；验收形态（新套件 + assert/summary + 退出码）与既有模式 1:1 同构。它同时是三个已落选 UI 候选的公共前置。 |

### 1.3 一句话定位

R3 = 给 e2e harness 装上"眼睛"：新增 1 个浏览器套件，用真实 chromium 驱动 **console 构建产物**（非 dev server），把"登录 → 仪表盘 → 记录浏览 → 编辑器写回 → 备份面板"五条用户路径从零覆盖变为 CI 红绿可判——其中编辑器写回做到 **UI 操作 → manifest 文件 → PB schema** 的三端交叉验证。产品代码零改动。

## 2. 用户故事

1. 作为**控制台的贡献者**，我修改 `App.tsx`（重构编辑器交互、调整备份面板）时，CI 用真实浏览器走过登录/编辑/备份路径，破坏性改动立刻红灯——而不是"UI 变更零覆盖、靠用户报障"。
2. 作为**维护者**，我改动编辑器写回链路（draft 组装、字段改名映射、save 校验）时，CI 断言"UI 里点保存"最终落到 manifest 文件内容、PB collection schema 与 `.bak` 文件三个可观测结果——UI 横幅出现不等于验证通过。
3. 作为**CI 维护者**，浏览器套件失败时自动留下截图与页面 console 日志（复用现有 `保留失败现场` artifact step），远程红灯可离屏诊断，无需本地复现。
4. 作为**后续迭代的产品 agent**，R4 的记录浏览增强等 UI 需求从此可按"arrange via API、act via UI、assert via UI"验收，R1 的否决理由正式失效。

## 3. 功能需求

约定：现有 7 套件 99 项断言**冻结**（文件逐字不动）；新增套件 `tests/suites/console-ui.test.mjs` 追加到 runner 套件列表**末尾**（security 之后，延续"污染型/依赖型套件排最后"纪律——本套件通过编辑器真实写回 manifest-project、在主实例创建/删除备份，是全部套件中污染面最大的）。runner 已支持 `--suite console-ui` 单跑调试。

- **FR-1 依赖与浏览器安装**：根 `package.json` devDependencies 新增 `playwright`（^1.x，库模式）。注意 pnpm 的 `onlyBuiltDependencies` 白名单机制会拦截 playwright 的 postinstall，`pnpm install` **不会**自动下载浏览器——浏览器一律由显式命令安装：CI 新增 step `pnpm exec playwright install --with-deps chromium`；README 增补本地一次性安装说明。套件启动时若 chromium 不可用，以带安装指引的错误**失败**（不允许静默 skip——"有浏览器套件但从未真正跑过"等于回到零覆盖且更隐蔽）。
- **FR-2 套件同构**：新套件遵循既有套件模式——环境变量取目标（`TEST_CTRL`/`TEST_PB`/`TEST_TMP`/`TEST_FIXTURE_DIR`，runner 已注入，**零新增**）、`helpers.mjs` 的 `assert/summary`、进程退出码即结果、runner 180s 套件超时。不引入 `@playwright/test` runner（其自带 runner/expect 与 `assert/summary` 模式冲突），用 playwright 库 + 手动等待原语。
- **FR-3 被测对象 = 构建产物**：被测页面是控制服务器（TEST_CTRL）托管的 `packages/console/dist` SPA，浏览器内登录直连主实例（TEST_PB）。runner 前置 `pnpm -r build` 已含 console 构建（CI 有独立构建 step）；dist 缺失时 `oneshot console` 显式报错，套件自然红灯——不额外做预检。
- **FR-4 arrange via API、act via UI、交叉验证**：测试数据准备与状态读取（超管 token、种子记录、读当前 manifest）用既有 HTTP helpers；UI 操作一律 playwright locator；关键写路径（编辑器保存）必须 **UI 断言 + HTTP/文件系统交叉验证**——成功横幅出现过不算验证，要落到 manifest 文件内容、PB collection schema、`.bak` 存在三个事实。
- **FR-5 场景清单**（五条路径，全部针对**既有** UI，不为测试发明新功能）：
  1. **登录**：登录表单可见；错误密码 → 错误横幅且不进入仪表盘；正确凭据（PB 地址填 TEST_PB，**不依赖 localStorage 默认值**）→ 仪表盘渲染项目名。
  2. **仪表盘**：manifest hash 与期望值一致（见坑位 6 的确定性做法）；服务列表渲染出 GET /api/manifest 读到的全部服务名；collection 记录数从 `…` 变为 ≥ 1 的数字。
  3. **记录浏览**：先经 API 播种一条唯一 title 的 tasks 记录（超管 token + `makeUser` 提供合法 owner），进 UI 表格断言该行可见（默认 `-created` 排序在首屏）、点击行后详情抽屉 JSON 含记录 id。
  4. **编辑器写回（核心）**：进入服务编辑器 → `+ 添加字段`（唯一名 `e2e_ui_<ts>`，options 留 `{}`）→ `写回 manifest 并发布` → 成功横幅"发布完成"；交叉验证 manifest 文件含新字段、PB schema 含新字段、`.bak` 存在。
  5. **编辑器客户端校验**：重新进入编辑器，把字段名改为含空格的非法名 → 保存 → 错误横幅含"字段名非法"；HTTP 侧确认 manifest **未被污染**（客户端校验拦截，未发请求）。
  6. **备份面板**：进入备份页 → 创建唯一名备份 → 列表出现 `<name>.zip` → 下载（`waitForEvent('download')`，`suggestedFilename` 为 `<name>.zip`）→ 删除（先注册 dialog accept，见坑位 3）→ 列表消失。
- **FR-6 稳定性纪律**：禁止固定 `waitForTimeout` 睡眠，全部依赖 locator 自动等待与 `waitFor({ state: 'visible' })`/事件等待；动态取值（服务名、字段清单、manifest 路径）一律 HTTP 侧先读再断言，不写死早前套件遗留状态（冻结 fixture 的 `title`/`created` 等稳定字段名可写死）；所有创建物命名带时间戳唯一化；失败时页面截图 + `pageerror`/console 事件缓冲写入 `TEST_TMP/console-ui-artifacts/`（CI 现有 artifact step 已上传 `tests/.tmp`，零编排改动）；全程收集未捕获页面异常并在收尾断言为零。
- **FR-7 计数与文档同步**：README"测试与 CI"计数 99 → 实际值、套件列表加 `console-ui`、补浏览器一次性安装说明；CI yml e2e step 名计数同步。
- **FR-8 零回归**：既有 7 套件文件逐字不动；`run-e2e.mjs` 除套件数组追加 `'console-ui'` 外无改动；`packages/*` 产品代码零改动——不允许为测试修改任何产品逻辑；文本选择器优先（控制台文案稳定且语义化），个别不稳定处允许给产品加 `aria-label`/`data-testid` **纯标记属性**（零逻辑、零视觉变化），须在 PR 中逐处说明。

## 5. 非目标（本迭代明确不做）

1. **不给控制台加任何新功能**：记录浏览增强（过滤/排序/搜索）是 R4 首选——本迭代交付的是它的验收能力，不是功能本身。本套件全部断言针对既有 UI。
2. **不测备份 restore**：恢复会重启 PB，慢且破坏现场（主实例被后续无套件依赖，但中途重启引入无谓脆弱）；create/list/download/delete 已覆盖面板主链路。
3. **不引入 `@playwright/test`**：runner/expect 体系与 `assert/summary` + 退出码模式不同构；用 playwright 库模式。
4. **不做视觉回归**（截图 diff 基线）：基线维护成本高、对字体/渲染环境敏感；布局正确性靠"关键元素可见 + 文本断言"替代。
5. **不测 PB Admin UI**：不是 OneShot 的产物；控制台与 Admin UI 的边界（控制台只是 manifest 的 GUI）由既有文档约束。
6. **不为测试改产品逻辑**：仅允许零逻辑的标记属性（FR-8）；若某场景必须改逻辑才能测，说明该场景超出本迭代，记录后放弃该断言。
7. **不做无浏览器环境的静默跳过**：缺浏览器 = 失败 + 安装指引。本地开发者一次性安装（README 写明），换取"CI 绿 = UI 路径真的跑过"的单一事实。
8. **不做移动端视口/响应式断言**：桌面 chromium 单视口即可；响应式属视觉回归范畴（见 4）。
9. **不做浏览器缓存优化**：CI 每次冷装 chromium 可接受（+1~2 分钟）；`actions/cache` 留实现者可选优化，不做硬性要求。

### 实现注意（坑位提示）
1. **pnpm 拦截 postinstall**：`onlyBuiltDependencies` 白名单只有 esbuild，playwright 的浏览器下载脚本不会随 `pnpm install` 执行。必须显式 `pnpm exec playwright install chromium`（CI 加 step、README 写一次性安装）。**不要**把 playwright 加进 `onlyBuiltDependencies` 让它隐式下载——显式命令才能被 CI 缓存与本地跳过。
2. **等待纪律**：禁 `page.waitForTimeout` 固定睡眠。locator 点击/填充自带自动等待；可见性用 `locator.waitFor({ state: 'visible', timeout })`；下载用 `page.waitForEvent('download')`。编辑器保存触发的真实 publish（diff 式）给 30s 上限，普通导航 10s 足够；全套件实测应 < 60s（180s 套件超时内的余量是给 CI 冷环境的）。
3. **`window.confirm` 默认被 dismiss**：备份"删除"按钮走 `confirm()`，playwright 不注册 handler 时默认取消——删除永远不生效，而"列表不再含该备份"会误报通过。必须 `page.on('dialog', (d) => d.accept())`（在进入备份场景前注册，勿全局误吞其他对话框）。
4. **登录页 PB 地址不依赖默认值**：输入框默认取 localStorage 或 `'http://127.0.0.1:8090'`，全新 context 下指向错误实例。三个输入框（地址/邮箱/密码）全部显式 `fill`，地址 = TEST_PB。
5. **排布先于行动**：manifest-project 在早前套件中经历过多次写回（manifest 套件增删过服务/字段后还原），服务与字段清单不可写死假设。套件开头 GET `/api/manifest` 读当前 config，服务名/字段名/manifest 路径全部动态取用。
6. **hash 期望值的确定性**：套件开头把 GET 到的 config **原样 POST 回去**（幂等 no-op diff，manifest 套件已有先例），保证 oneshot_meta 最新记录与当前 config 一致；期望 hash 用 core dist 的 `snapshotHash(buildSnapshot(config))` 对同一 config 计算。若实测发现 config 含环境展开导致两侧 hash 不一致，降级为"仪表盘 hash === meta 记录集（filter project）中任一 hash"并在 PR 说明。
7. **编辑器保存场景是安全的**：control-api 的 POST 走默认 hooksDir（`manifest-project/pb_hooks`），主实例仍加载 `hooks_main`，无 hooks 热重载副作用；collection schema 变更是 API 级即时生效。不要顺手去断言 hooks 产物（它们不落在主实例的 hooks 目录）。
8. **命名唯一化**：字段名/备份名/记录 title 一律 `e2e_ui_<ts>` 前缀，避免与早前套件残留（如 manifest 套件的 `e2e_field`）及 `--keep` 调试现场冲突。
9. **失败诊断产物**：监听 `page.on('pageerror')` 与 `page.on('console')` 缓存事件，任一断言失败或套件 catch 时连同 `page.screenshot()` 写入 `join(TEST_TMP, 'console-ui-artifacts')`——CI"保留失败现场" step 已上传整个 `tests/.tmp`，零编排改动。AC-8 断言只认 error 级页面异常，React 开发警告不算。
10. **排最后 + 可单跑**：本套件写回 manifest-project、增删主实例备份，污染面全 suite 之最，必须排 security 之后；runner 的 `--suite console-ui` 单跑模式（只拉起环境 + 本套件）可直接用于开发调试。
